AnthropicのCEOダリオ・アモデイ氏は、オープンウェイトモデルの禁止には反対しつつ、国家安全保障の観点からチップ輸出規制、産業規模の蒸留阻止、および全モデルへの安全性テストを提唱した。

AnthropicのCEO、ダリオ・アモデイ氏は、同社がオープンウェイトモデルの禁止を画策しているという誤解に対し、明確な立場を表明しました。同氏は、危険な機能を持たないオープンウェイトモデルは「公共財」であると認め、それ自体の禁止は有用な手段ではないと述べています。一方で、権威主義国家によるAIの軍事利用や、生物・サイバー攻撃への悪用という重大な懸念に対処するため、以下の3つの対策を提案しています。

## DebianにおけるLLM（大規模言語モデル）使用に関する一般決議 (GR)

https://www.debian.org/vote/2026/vote_002

**Original Title**: General Resolution: LLM usage in Debian

Debianプロジェクト内での生成AI（LLM）の使用について、全面禁止から条件付き容認まで、5つの異なるアプローチの提案が一般決議（GR）として議論されている。

Debianプロジェクトにおいて、LLMを用いた貢献の是非を問う一般決議の提案内容が公開されました。主な提案は以下の5つです。

1. **案A（全面禁止）**: 社会契約を改訂し、パッケージングやドキュメント作成など、プロジェクトへの直接的な貢献におけるLLMの使用を全面的に禁止する。著作権の不透明性、品質の低下、コミュニティへの負荷、倫理的懸念を理由としている。
2. **案B（ガイドライン付き容認）**: ツールの法的適合性、提出者の自己責任、AI使用の開示、大量変更の事前相談を条件に利用を許可する。
3. **案C（可能な限り拒絶）**: 人間へのメッセージ（バグ報告やメール）への使用を禁止し、可能な限りLLMを避けるよう要請する。メンテナは自身のプロジェクトでLLMを禁止できる権限を持つ。
4. **案D（責任ある使用の受入）**: 禁止は非現実的であるとし、提出者が内容を完全に理解・説明できることを条件に、Debian固有の作業への使用を認める。
5. **案E（既存基準の維持）**: LLMを特別視せず、既存の品質・法的基準をそのまま適用する。特別な禁止も推奨も行わず、最終的な責任は常に提出者にあるとする中立的な立場。

これらの提案は、自由ソフトウェアコミュニティにおけるAIの法的・倫理的立ち位置を決定付ける重要な議論となっています。

## MCP 2026-07-28 仕様のリリース：ステートレス化とエンタープライズ向け拡張性の向上

## Cursor・Manus・Spotifyの「ハーネス」を読み比べた

https://zenn.dev/tak3/articles/2686517823d1e7

Cursor、Manus、Spotifyなど先進6社のエンジニアリングブログから、AIエージェントの性能を左右する「ハーネス（周辺回路）」の設計思想を6つの要素で解像度高く比較・分析した記事。

この記事は、AIエージェントの実装における「ハーネス（harness）」、すなわちモデルの周囲を固めるループ、ツール、コンテキスト管理、ガードレールなどの設計思想を、先進企業6社（Cursor, Manus, Mozilla, Spotify, Ramp, Shopify）の公開情報を元に比較・整理しています。

### ハーネスを構成する6要素
著者はハーネスを「ループ」「ツール実行系」「コンテキスト管理」「統制」「状態・実行環境」「観測」の6要素に分解し、各社の強みを分析しています。

### 各社の特徴的な設計
- **Cursor**: モデルの癖（パッチ形式か置換か等）に合わせた個別最適化と、「Keep Rate」等の独自の観測指標を重視。
- **Manus**: KVキャッシュヒット率を最重要視し、ファイルシステムを究極のコンテキストとして扱う設計。
- **Mozilla**: セキュリティバグ修正のため、エージェント自身に「再現テスト」を実行させ仮説検証を行うループを構築。
- **Spotify**: Claude Agent SDKを自社ラッパーで包み、ビルドやテストが通らない限りPRを出さない厳格な検証ゲート（統制）を設置。
- **Ramp**: エージェントをモデル知能の限界まで解放するため、全SaaSツールを配線し全コンテキストを渡す思想。
- **Shopify**: システムプロンプトの肥大化を防ぐため、ツール実行時に必要な指示を動的に渡す「JIT instructions」を提唱。

### 結論
エージェントの信頼性は、モデルの賢さ以上に「出す前に検証し、通らなければ出さない」という検証ループの有無に依存しており、ハーネスは進化し続けるモデルへの追従装置として機能していると結論づけています。

## 1日500コミットは、もう読めない ── だからコードレビューをやめた

https://zenn.dev/singularity/articles/stopped-reviewing-my-code

AIエージェントによる超高速な開発サイクルにおいて、人間がコードを読まずに品質を担保するための、厳格な自動検証とAI同士の相互レビューを軸とした新しい開発パラダイムの提言。

AIエージェントを並列稼働させ、1日500件ものコミットが生成される環境では、人間によるコードレビューは物理的に不可能です。本記事では「読まなくても壊れない」状態を維持するための具体的な戦略が公開されています。主な手法として、①AI用の規約ファイル（CLAUDE.md）によるスタックの統一、②ESLintやSonarJSを用いた「人間なら耐えられないほど厳しい」静的解析、③ロジックをPure関数に集約し、AIにエッジケースを網羅させるテスト設計、④実装したAIとは別のモデルによるGitHub Actions上での自動レビュー、の4点が挙げられています。著者は、ボトルネックが「書く速度」から「判断と統合の速度」へ移行したことを指摘し、エンジニアの役割が「コードを読む」から「動く画面を見て判断する」ものへと変容している現状をリアルな実体験に基づいて綴っています。
