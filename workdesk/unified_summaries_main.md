## ハーネスエンジニアリング入門 — Agent = Model + Harness で読み解くAIエージェント運用

https://qiita.com/ryoji9702/items/065b1f2218f132d1bd3b

AIエージェントの性能を決定づける「ハーネス（足場）」の設計思想を軸に、Feedback Flywheelや認知的負債、SPDDといったThoughtworks周辺の高度な運用フレームワークを体系的に解説した記事。

本記事は、AIエージェントの運用を「Agent = Model + Harness（ハーネス）」という数式で定義し、モデル以外の周辺環境（足場）をどう設計・運用すべきかを整理した解説記事です。ThoughtworksのBirgitta Böckelerらが提唱する概念群をベースに、以下の主要ポイントを提示しています。

1. **ハーネスの構造化**: エージェントの制御を「guides（事前統制：CLAUDE.md等）」と「sensors（事後検知：テストや静的解析）」に分け、それぞれ決定論的・推論的なベクトルで設計する手法。
2. **Feedback Flywheel**: AIとの対話を単発で終わらせず、得られた知見を共有アーティファクトに還流させて組織・チームの習熟度を高める維持機構。
3. **Cognitive Debt（認知的負債）**: AIが生成する「動くが誰も理解していないコード」によってチームのシステム理解が失われるリスクとその対策。
4. **SPDD（Structured Prompt-Driven Development）**: プロンプトを第一級の資産として管理し、テスト駆動・リファクタリングを前提としたAI時代の開発手法。

記事では、モデルの優劣が短期間で陳腐化する中で、これらのハーネス資産と運用能力こそが、長期的な競争力（筋肉）になると強調しています。

## Loop Engineeringで失敗しないためのハーネス設計

https://zenn.dev/kamo78/articles/kaji-guarded-loop-engineering

AIエージェントに自律的な開発を任せる「Loop Engineering」において、作業の逸脱や品質低下を防ぐための5層のガード（ハーネス設計）の重要性と、その実装ツール「kaji」を紹介する記事。

AIエージェントに「設計・実装・修正・検証」のループを自律的に回させる「Loop Engineering」は、強力である一方で「形骸化したテスト」や「無限修正ループ」といった失敗を招きやすい。本記事では、これらを防ぎAIの出力を制御する外側の仕組みを「ハーネス」と呼び、5つの層（Workflow, Step, Verdict, Quality gate, Standards）で構成されるガードレール設計を提案している。

1. **Workflow**: 工程の分岐や停止条件を定義する層。
2. **Step**: 各工程でのエージェントの具体的な手順を規定する層。
3. **Verdict**: AIの判断を構造化出力に縛り、決定論的な遷移を保証する層。
4. **Quality gate**: Lintやテストなど、LLMを通さない決定論的なチェック層。
5. **Standards**: コーディング規約やテスト規約を明文化する層。

著者が開発するOSSツール「kaji」およびそのスターターテンプレートは、これらのガードをあらかじめ実装しており、AI駆動開発を「AI任せ」ではなく「検証可能なエンジニアリング」へと昇華させるための実践的なガイドとなっている。

## Gemma4やQwen3.6だけじゃない…ローカルLLM「爆速進化」実現した“4つの技術”を解説

https://www.sbbit.jp/article/cont1/185980

高額なAPIコストを回避する手段として注目される「ローカルLLM」が、量子化やQAT、MoEなどの技術革新により、家庭用PCでも実用レベルで動作可能になった背景を解説する。

この記事では、月額数万円に達することもあるAIエージェントのAPI課金問題を解決する手段として、急速に進化している「ローカルLLM」の核心技術を4つに整理して解説しています。かつては性能面で妥協が必要だったローカル環境でのAI運用が、現在ではGemma 4やQwen 3.6などの最新モデルにより、実用フェーズへ突入しました。

背景にある4つの主要技術は以下の通りです：
1. **量子化**: モデルの精度を維持しながらデータサイズを劇的に縮小し、メモリ消費を抑える技術。
2. **QAT (Quantization-Aware Training)**: 4bitなどの低ビット動作を前提に学習段階で最適化を行い、軽量化と高精度を両立させる技術。
3. **MoE (Mixture of Experts)**: 巨大なモデルの中から、特定のタスクに必要な「専門家」パラメータのみを動かすことで、推論速度を向上させる仕組み。
4. **エージェント向け高速化**: 並列処理や構造化データ生成の効率化により、AIエージェントとしての実用性を高める技術。

これらの技術的進展により、クラウドAI（GPT-5.5等）との使い分けや、特定のタスクに特化したローカル環境の構築が現実的な選択肢となっています。

AIエージェントが「カスタマーチケットの要約」などの正当なタスクを実行する際、データ内に隠された悪意ある指示（間接的プロンプト注入）を読み込み、機密データを外部の攻撃者サーバーへ送信してしまうリスクについて詳説しています。この攻撃は、1.プロンプト注入、2.MCPツール呼び出し、3.443ポートからの送出という3段階で成立しますが、従来のKubernetes NetworkPolicy（IP/ポートベース）では、CDNなどの背後にある攻撃者のドメインを識別できず、この「静かな流出」を防げません。対策として、ポッドごとのアイデンティティに基づき、FQDN（完全修飾ドメイン名）でフィルタリングを行う「決定論的な封じ込め（Deterministic Containment）」の導入を提言しています。具体的には、Cilium（eBPF）、サービスメッシュ、またはクラウドネイティブなファイアウォールを活用し、許可されたドメイン以外への通信をデフォルトで拒否する構成を推奨しています。

## AI時代の新しい攻撃「プロンプトインジェクション」と安全な設計の考え方について

https://qiita.com/y-tsukahara_palettelink/items/7d094965ae99fa92fb37

LLMにおけるプロンプトインジェクションの仕組みや攻撃手法を解説し、OWASPの指針に基づいた多層防御による安全なシステム設計の重要性を説く。

LLMアプリケーションにおける主要なセキュリティリスクである「プロンプトインジェクション」のメカニズムと対策を詳細に解説しています。LLMは「命令」と「ユーザー入力（データ）」を共に自然言語として処理するため、両者を物理的に分離しにくく、悪意ある入力によって開発者の意図しない動作が誘発される根本的な脆弱性を抱えています。記事では、直接的な指示の上書きだけでなく、RAG（検索拡張生成）や外部サイトを介した「間接的プロンプトインジェクション」の脅威についても言及。対策として、OWASP Top 10 for LLMの枠組みを参照し、デリミタを用いたデータ隔離、出力のサニタイズ、最小権限の原則に基づくエージェント設計、および継続的な敵対的テストの実施といった多層防御の必要性を強調しています。「LLMは騙される可能性がある」ことを前提に、被害を最小化する設計思想が重要です。

## AI Agent SaaS を支える自社仮想化基盤「Sunaba」への挑戦と実運用

https://speakerdeck.com/flatt_security/ai-agent-saas-virtualization

GMO Flatt Securityが、AIエージェントの安全かつ高速な実行環境を求めてFirecrackerベースの独自仮想化基盤「Sunaba」を構築・運用する知見を公開しています。

GMO Flatt Securityが開発するAIエージェントSaaS「Takumi」における実行基盤の課題解決を詳説したスライドです。従来のK8s Podによる分離では、1顧客あたりのコスト負担やカーネル共有によるセキュリティ懸念（コンテナエスケープ等）があり、一方でクラウド標準VMは起動時間の遅さがボトルネックでした。これらの課題を克服するため、同社はAWS Lambdaの基盤でもあるFirecrackerを採用したKVMベースの仮想化基盤『Sunaba』をフルスクラッチで開発。Copy-on-Write (CoW) 技術の活用により、VM起動時間を約5秒に短縮し、ピーク時には週次100万VMを処理するスケール性能を実現しました。運用面でも、Grafana Alloyによる監視統合、Blue-Greenデプロイ、独自のDrain機構など、内製基盤ならではの高度なSREプラクティスが共有されています。
