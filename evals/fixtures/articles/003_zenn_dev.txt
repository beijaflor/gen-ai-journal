CodetechAIに書かせた日本語を読んで、「整っているのに、どこか不自然」と感じたことはないだろうか。 誤字はない。文法も合っている。それなのに、地の文がつるりと滑って頭に入ってこない。「AIが書いた文章だ」と一目で分かる、あの感じ。 この「整いすぎて不自然」には、正体がある。名前もついている。カルク（calque＝翻訳借用）——英語をそのまま直訳して日本語に取り込む現象だ。 そして厄介なことに、これは整って見える文章ほど見つけにくい。本記事の後半で、私がAIに書かせて公開した自分の技術記事を題材に、自作スキルで実際に検出した結果を全部さらす。一読すると破綻のないAIの文章から、5件の欠陥が出た。 カルク（翻訳借用）とは何か カルク（calque）とは、外国語の語や成句を、構成要素ごとに直訳して日本語に取り込むことだ。日本語では 翻訳借用 という。skyscraper →「摩天楼」、honeymoon →「蜜月」、iron curtain →「鉄のカーテン」。これらは定着した正規の日本語で、それ自体は欠陥ではない。 問題になるのは、慣用句や構文を直訳した結果、不自然な日本語＝訳語臭（翻訳調）になるときだ。単語が間違っているのではない。構造が英語のまま——それが、あの「整いすぎて不自然」の正体である。 見分け方は一つ、逆翻訳テスト。怪しい箇所を英語に戻し、英語の慣用句や有標な構文にそのまますっぽり戻るなら、直訳カルクを疑う。 「同じページにいる」→ "on the same page" → 日本語なら「認識が揃っている」 「テーブルの上にある」→ "on the table" → 日本語なら「検討中だ」 「針を動かす」→ "move the needle" → 日本語なら「効果を出す」 ただし注意がいる。普通の文がただ普通の英語に戻るだけ（「私は学生です」→ "I am a student"）や、摩天楼のような定着語は、叩いてはいけない。ここを取り違えると、自然な日本語まで赤を入れてしまう。擬陽性こそが最大の敵だ。この一線は後でもう一度効いてくる。 一番よく出て、一番気づきにくい型：無生物主語 実例で一番多いのは、語ではなく構文の直訳——無生物主語＋他動詞だ。英語の "X enables Y" / "the file lowered the score" をそのまま訳すと、日本語でも「ファイルがスコアを下げる」と書いてしまう。厳密には、これは語の借用というより構文レベルの翻訳調だが、「英語をそのままなぞる」メカニズムはカルクと同じで、本スキルもまとめてカルクとして拾う。 文法は正しい。誤解もされない。だが、日本語の地の文としては不自然に響く。日本語は「人が何をしたか」「何がどうなったか」で書くほうが自然で、「モノがモノにこうさせた」と書くと、訳文の匂いが立つ。 AIがこの構文を量産するのは、英語が主体の学習データの構造を、確率的になぞるからだ。翻訳者の手に残る訳語臭と、同じ仕組みで生まれる。だから——次に示すように——AIに書かせて公開した自分の記事にかけると、まさにこの型が並ぶ。整って見えるAIの文章を、そのまま解剖する。 これは、感じるのに言葉にできない欠陥の典型だ。読み手は「なんか硬い」としか言えない。名前を与えると直せる。 自分の記事で実演する（ドッグフーディング） ! ※ この実演の題材も、私が AIに書かせて 公開した記事だ。だからこそ、AIのカルクがそのまま出た。「整いすぎて不自然」の正体を、借り物の例ではなく、AIの文章そのもので見せる。 きれいごとを並べても仕方ない。AIに書かせて Zenn に公開した自分の記事に、自作スキル jp-style-check を実際にかけた。 題材は「Claude Codeが廃案を実装し直す『コンテキスト・ドリフト』を止めるドキュメント管理術」。構成も日本語も、一読すると整っている。それでも、訳語臭は出た。 スキルの出力は確度で2層に分かれる。〔指摘〕 は反証可能な欠陥、〔助言〕 は確度の低いリズム系の助言。場所・理由・直し方を返す。美しさの点数は出さない（理由は後述）。 〔指摘〕1 カルク（無生物主語） Before：LLMが自動生成したリポジトリレベルのコンテキストファイルは、タスク成功率を平均3%低下させ、推論コストを20%以上増加させた。 逆翻訳すると "the context file lowered the task success rate by 3% and increased inference cost by 20%+"。無生物主語＋使役他動詞の、英語そのままの形に戻る。 After：コンテキストファイルを与えると、タスク成功率は平均3%下がり、推論コストは20%以上増えた。 「ファイルが下げた」をやめ、「与えると下がった」にする。主語をモノから出来事へ移すだけで、訳語臭が消える。 〔指摘〕2 カルク（一語訳） Before：リポジトリレベルのコンテキストファイル "repository-level" の一語訳。辞書の一番目をそのまま当ててしまう型だ。 After：リポジトリ全体の／リポジトリ単位の 単語は慣用句でないので逆翻訳テストに掛かりにくい。だからこそ取りこぼしやすい。level → レベル、native → ネイティブ、status → ステータス は、一度疑う価値がある。 〔指摘〕3 カルク（無生物主語＋名詞化） Before：無秩序な情報の追加は、AIに過剰なファイル探索と無駄なテストを促し、本質的なタスクの解決を阻害する。 「情報の追加は……促し……阻害する」。これも無生物主語で、しかも「追加」「解決」と動作が名詞に固められている。 After：情報を無秩序に増やすと、AIは余計なファイル探索や無駄なテストに走り、本来解くべきタスクから遠ざかる。 名詞化をほどいて動詞に戻すと、誰が何をするかが立ち上がる。 〔指摘〕4 簡潔（名詞化で動作主が消える） Before：物理的なアクセス制限を設けることで、過去の記憶の改ざんという挙動を排除する。 「改ざんという挙動を排除する」は、何が何をするのかが抽象の層に隠れている。 After：物理的なアクセス制限を設け、過去の記録が改ざんされること自体を防ぐ。 〔指摘〕5 明快（略語が未定義） Before：いずれも、LLMの注意機構の偏り（Lost in the MiddleとCDV）を構造の側から補う設計である。 CDV がまとめで初めて出てくる。本文では「コンテキストヘッド」という語で説明していたのに、結論で別の略語に化けた。読者は CDV を知らない。 After：初出で CDV（文脈による注意の希釈） と定義するか、本文で使った「コンテキストヘッド」に語をそろえる。 そして、ここが大事 — 出なかった箇所 コンテキスト内にタスクと無関係な情報（ノイズや廃案のログ）が混入すると、「コンテキストヘッド」は関連情報へ十分な注意を割り当てられなくなる。 この文には、スキルは何も指摘を返さなかった。主述は通り、解釈は一意で、訳語臭もない。「ここは問題なし」と黙ることこそ、検出器の価値だ。何にでも赤を入れる校正は、すぐ信用されなくなる。 なぜ「採点」ではなく「欠陥検出」なのか ここがこのツールの設計思想で、たぶん一番伝えたい点だ。 世にある「AIが美しい日本語を書く」の類を、私はいったん全部疑っている。理由は単純で、美しさは安定して測れないからだ。LLMは音を聞けないし、滋味や品格を一貫した基準で採点できない。できるふりをすれば、その場の気分で揺れる点数が出るだけだ。 だから、このスキルは美しさを採点しない。代わりに、反証可能な欠陥だけを叩く。主述のねじれ、一文二義、訳語臭、未定義の略語、表記ゆれ——「ここが、こういう理由で、こう直る」と示せるものだけを指摘する。確度の低いリズム系は 〔助言〕 に落とし、確度を正直に分けて示す。 擬陽性を抑えることが、欠陥検出器の生命線だ。だから、文学的・カジュアルな文体では、反復強調も意図的な語格の切替も「正当」と判断して指摘しない。 2つのスキル 配布物は Claude Code のプラグインで、スキルは2点だ。 jp-style-check — 日本語の明快さだけを見る。簡潔・明快・誤解されない＋一貫性（用語・表記・語格）。「読みにくい」「簡潔にして」「これ翻訳調になってない？」のときに使う。 logic-jp-check — 同じ日本語チェックに論理層を足す。波頭亮『思考・論理・分析』に沿って、主張と根拠の対応、帰納・演繹、MECE、因果を点検する。文章に加えて論証も見たいときに使う。
