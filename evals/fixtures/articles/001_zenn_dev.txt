Think of this file as giving Claude an overview of your codebase, or as an index pointing to other files where Claude can find more information as needed. ルートの CLAUDE.md はセッション開始時に全量ロードされ、コンパクション後も再読み込みされます。つまりリポジトリで作業する全メンバーが毎セッション支払うコンテキストコストです。内容が膨らむほど、実際の会話やコードに使える領域が狭まり、指示への追従精度が下がったりコンパクションが早期に発生したりします。 200行以下を目安にし、所有者を明示してコードと同様にレビューする 特定ディレクトリにしか関係ない規約はサブディレクトリ CLAUDE.md か .claude/rules/（パス条件付き） に移す 手続き的な手順（デプロイフロー等）は Skills に切り出す（後述記事参照） 使い分けの実践例 # ~/.claude/CLAUDE.md（User — 個人の全プロジェクト共通） - 日本語で応答する（コード・変数名は英語） - Conventional Commits 形式でコミットメッセージを書く - 確認なしに自動コミット・自動 push しない # ./CLAUDE.md（Project — チーム共有） - TypeScript strict mode を使用する - テストは Vitest で書く - API レスポンスは統一フォーマット { data, error, meta } で返す # ./CLAUDE.local.md（Local — 個人のプロジェクト固有） - デバッグ時は console.log ではなく debugger を使う - 自分のローカル DB は port 5433 で動いている @ インポート構文 CLAUDE.md 内で外部ファイルを参照できます。共通のナレッジを別ファイルに切り出し、複数プロジェクトから取り込むのに便利です。 # ~/.claude/CLAUDE.md @~/.claude/instructions/typescript-conventions.md @~/.claude/instructions/git-workflow.md .claude/rules/ — トピック別のルール分割 CLAUDE.md が長くなりすぎる場合は、.claude/rules/ にトピック別のファイルを配置できます。paths frontmatter でグロブ指定すると、該当ファイル操作時のみロードされてコンテキストを節約できます。 --- paths: - "src/api/**/*.ts" - "**/*.handler.ts" --- # API ルール - すべてのエンドポイントで認証ミドルウェアを使用する - レスポンスは統一フォーマットで返す - 入力バリデーションは Zod で行う スコープ 配置場所 User ~/.claude/rules/ Project .claude/rules/ Rules と CLAUDE.md の使い分け: Rules: ファイル固有の制約（「マイグレーションファイルは追記のみ」「API ハンドラは必ず入力バリデーションする」） CLAUDE.md: コードベース全体に適用される事実情報（ビルドコマンド、アーキテクチャ概要） パススコープ Rules は「複数箇所に散在する横断的関心事」に最適です。API 規約、テスト方針、セキュリティルールなど、特定のファイルパターンにだけ適用したいルールを効率的に管理できます。 モノレポでの運用 モノレポでは各チームのディレクトリにサブディレクトリ CLAUDE.md を置き、チームごとに自分のコンベンションだけをロードさせるのがベストです。 services/ ├── auth/CLAUDE.md # 認証チーム固有 ├── payments/CLAUDE.md # 決済チーム固有 └── api/CLAUDE.md # API チーム固有 不要なサブディレクトリの CLAUDE.md を除外するには claudeMdExcludes 設定を使います: // .claude/settings.json { "claudeMdExcludes": ["services/legacy/**"] } settings.json — Claude Code 本体の動作設定 役割 settings.json は Claude Code 自体の動作を制御するファイルです。モデル選択、権限ルール、環境変数、フックなどを設定します。 スコープと配置場所 スコープ 配置場所 git 共有 用途 User ~/.claude/settings.json — 個人の全プロジェクト共通設定 Project .claude/settings.json ○ チーム共有設定 Local .claude/settings.local.json ✗ 個人のプロジェクト固有設定 優先順位 CLI引数 > Local > Project > User（最弱） マージの挙動 ここが settings.json を理解する上でのポイントです。 値の種類 マージルール スカラー（model, theme 等） 高優先スコープが勝つ 配列（permissions.allow/deny/ask） 全スコープから連結・重複排除（上書きではない） オブジェクト（env, hooks 等） deep merge つまり permissions.deny に書いたルールは、どのスコープに書いても全部効きます。Project で deny したものを Local の allow で打ち消すことはできません。 設定例 { "model": "claude-sonnet-4-6", "effortLevel": "high", "permissions": { "allow": [ "Bash(npm run *)", "Read", "Edit" ], "deny": [ "Bash(rm -rf *)" ] }, "env": { "NODE_ENV": "development" } } 権限モデル — allow / deny / ask の評価ルール Claude Code の権限モデルは「ツールの実行に対して許可・拒否・確認を制御する」仕組みです。 評価順序（固定） 1. deny → マッチしたら即ブロック 2. ask → マッチしたらユーザーに確認 3. allow → マッチしたら自動許可 4. いずれにも該当しない → 初回使用時にプロンプト表示 最も重要なルール: deny は最強です。 どのスコープに書いても、他スコープの allow では打ち消せません。これはセキュリティのために意図的にこう設計されています。 ルール記法 { "permissions": { "allow": [ "Bash(npm run *)", "Bash(git status)", "Read", "Edit(/src/**/*.ts)" ], "deny": [ "Bash(rm -rf *)", "Bash(git push --force *)", "Read(.env)" ], "ask": [ "Bash(git push *)", "Bash(docker *)" ] } } パターン 意味 Bash(npm run *) npm run で始まるコマンドすべて Read すべてのファイル読み取り Edit(/src/**/*.ts) src 以下の .ts ファイル編集 Read(.env) .env ファイルの読み取りをブロック ファイルパスは gitignore 構文に準拠します。/path はプロジェクトルートから、~/path はホームディレクトリから、//path はファイルシステムルートからです。 権限モード モード 挙動 default 初回使用時にプロンプト、選択を保存 acceptEdits ファイル編集は自動許可、危険操作のみ確認 plan 読み取り専用で探索、編集前にレビュー auto バックグラウンド安全チェック付きで自動承認 dontAsk 事前に allow した操作以外は自動拒否（確認プロンプトを出さない） bypassPermissions サンドボックス環境向け。ほぼ全承認 /permissions コマンドで対話的に管理できます。また /fewer-permission-prompts を使うと、過去のセッションから頻繁に承認したコマンドを分析し、allow ルールに追加してくれて便利です。 設定ファイルの全体マップ ここまでの内容を俯瞰すると、Claude Code が参照するファイルは大きく3系統あります。 系統 代表ファイル 何を制御するか 指示 CLAUDE.md, .claude/rules/ Claude の振る舞い・判断基準 設定 settings.json
